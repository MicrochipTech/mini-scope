# Card 1.1: virtual motor in `firmware/tune_model.h`

Files: `firmware/tune_model.h` (new), `firmware/example_main.c` (structs, interrupt),
`docs/evidence/m1/` (harness, MDB scripts, raw output). Raw output of every run below is in
`docs/evidence/m1/*.txt`. Nothing here is a hardware result.

## What was built

- `tune_model.h`: `tune_model_step()` every 100 us. Current loop on every call, start sequence,
  speed loop and heartbeat on every tenth call. Names only: `motor`, `startup`, `tune_alive` come
  from the including file. States 0 stopped, 1 align, 2 ramp, 3 closed loop. Faults: 1 overspeed,
  2 synchronism lost, 3 align current too low, 4 handover speed too low, 5 heartbeat.
- `example_main.c`: structs `tune_motor` and `tune_startup` with a comment per member (role and
  script), `motor`, `startup`, `tune_alive` as volatile variables with defaults (kp 300, ki 60,
  current_kp 200, current_ki 20, ramp_rate 100, align 400, handover 600). Model interrupt on SCCP1
  at 10 kHz, priority 3. If `SCOPE_TIMER` is `SCOPE_CCP1` the model takes SCCP2 instead (checked by
  building with that setting: both `_CCT1Interrupt` and `_CCT2Interrupt` end up in the ELF). In the
  simulator build the interrupt sets `_U1TXIF`, with a comment why.
- Model choices that are mine, not from the plan: `ramp_rate` is counts per 10 ms; align takes
  100 ms and needs `align_current` of at least 300; the ramp needs 0.8 counts/ms of acceleration per
  count of align current minus friction (speed/64); the position estimate needs 300 counts at
  handover; closed loop reference is 1500 counts plus `ref_offset`; `iq` limit 1400; overspeed fault
  above 2500 counts. `motor.speed_ref` is the reference in use (ramp value in state 2, 1500 +
  `ref_offset` in state 3). The speed loop starts from zero iq at handover.
- Heartbeat: armed by the first change of `tune_alive`. After 1000 ms without change the model
  writes `run = 0` and `current_ref = 0`, stops, sets fault 5, and ignores `current_ref` until
  `tune_alive` changes again. Fault is cleared when `run` is 0 and the heartbeat is not lost.
- 16 bit safety: every product is cast to `int32_t` first, narrowing casts follow a clamp, no
  division (a first version with `/ 10` cost 1600 cycles in the slow pass, now 720).

Rise time is 10 to 90 % of the final value of the capture. kp 400 gives 500 us (limit: at least 300
us), kp 800 gives 200 us, so two samples at 100 us.

Speed loop, step of `ref_offset` from 0 to 500 at 1500 counts (overshoot % of the step, sign changes
of speed minus 2000 in the last 300 ms, peak `iq`):

- good region kp 200 to 500 with ki 30 to 120: overshoot 0 to 12 % (0 to 5 % from ki 60 up), no oscillation
- low gains (kp 50, ki 10): slow, no overshoot
- kp 1500 and more: overshoot 27 to 82 %, and with ki 1000 it oscillates (50 sign changes)
- kp 4000: fault 1 (overspeed above 2500) for every ki
- ki 1000 with kp 50 and 100: fault 1, with kp 200: oscillates (4 sign changes), kp 50 faults already at the start

So the unstable region ends in overspeed fault or in a limit. The map is the model's own; no
`tune_speed.py` exists yet, so nothing was run against it.

## Check 2: configuration `sim` in MDB

Build as in `start_sim.bat` (generator, then `make -f Makefile CONF=sim build`), no warnings.
Addresses from the ELF (`xc-dsc-nm`): `motor` 0x235C, `startup` 0x2376, `tune_alive` 0x100A, members
are 16 bit at consecutive even offsets in the order of the struct. Driver:
`python docs/evidence/m1/m1_mdb.py`, output in `mdb_run.txt`. It streams `motor.state`, `speed`,
`iq`, `fault` at 1 ms through the Scope protocol and writes `motor.run` and the `startup` members
with the `W` command. 0 samples lost in all phases.

| Start | MDB (ms after the first state change) | Result |

| ramp 400 | ramp at +100, fault 2 at +101 | fails |

Also a current step of 500 at standstill: `motor.current` rises to 480 after 6 ms and 494 after 12

## Check 3: host against MDB

State change times agree to the millisecond in all seven starts (the host counts from the run
write, MDB from the first state change, so host values minus 1): host 100/160 for ramp 100, 100/130
ramp 200, 100/220 ramp 50, fault 2 at 101, fault 4 at 115, fault 3 at 100. Run-down 40 ms in MDB
against 41 ms on the host, from a different cruise speed (1474 against 1501). Limit was 2 ms.
Current step: MDB 480 / 494 after 6 / 12 ms, host 483 / 494. The samples are every sixth
millisecond and the write time is known to about a millisecond, so this is a coarse check. No width
bug was found. Not compared: speed values in closed loop sample by sample.

## Check 4: interrupt load in MDB

`python docs/evidence/m1/m1_load.py` builds a throwaway copy that reads SCCP2 (FP/4) at the start and
end of the interrupt, with the stream running and the motor in all four states
(`load.txt`). Body only, with the simulator's TX kick, without the 20 cycles or so of
interrupt entry and exit:

- fast pass (9 of 10): at most 304 cycles
- slow pass: at most 720 cycles (state 0: 460, 1: 464, 2: 504, 3: 720)
- average over 17196 passes: 326 cycles = 10.2 % of 100 us at 32 MIPS (limit about 40 %)
- worst single pass 22.5 %. `scope_overflows` 0, 0 samples lost.

The first version had a slow pass of 1600 cycles (50 %), caused by two 32 bit divisions. It was
replaced by shifts and measured again.

## Not tested

- Real hardware. Interrupt priority, timer clock and ISR cost on a device are open. MDB cycle counts
  come from the simulator.
- gcc against XC-DSC results beyond the start times and the current step above; the harness only
  runs with gcc. The code avoids plain `int` arithmetic on purpose but this is not proven by a
  second compiler run of the harness.
- `tune_speed.py` and the delivered scripts themselves (they do not exist in the tree yet). The
  numbers were taken from the appendix of the plan.
- The model in `SIM` (card 1.2), the heartbeat in MDB (host only).
- `SCOPE_TIMER = SCOPE_CCP1`: built only, not run.
