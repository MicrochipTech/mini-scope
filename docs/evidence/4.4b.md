# Card 4.4b: intermittent stalls on the MDB port

Base 9b773d6. Machine: 2 performance, 8 efficient and 2 low power cores, on mains power, mostly idle otherwise. All scripts of
this card stayed in a scratch folder. Target time comes from the MDB command `Stopwatch`, which answers during a run and does not
depend on the UART file: cycles / 32 MHz. "Speed" is wall clock seconds per target second.

## Result

| Event | Result | Reproduced |
|---|---|---|
| B, slow merge runs | Cause found: Windows power throttling (EcoQoS) of the Java process. Fixed. | Yes, 14 to 77 on demand |
| A, stream stop in the probe | Not found. Several causes excluded. | 0 of 17 probes, 0 in 45 min of stream |
| C, E401 on the first ping | Not found. | 0 of 17 probes, 0 repeats in one GUI test |
| D, page vanished | Not found. No event loop lag, no ping timeout in the one session measured. | 0 in one GUI test |

They do not share a proven cause. B alone does not produce A: 15 minutes in the slow state showed no gap.

## B: power throttling

Same MDB, stream, 2 s Stopwatch, 60 s per phase (settling 8 s), set from outside on the Java process:

| Phase | Mean | Min | Max |
|---|---|---|---|
| free, first minute | 45.3 | 32.0 | 60.6 |
| performance cores only | 22.9 | 18.8 | 26.5 |
| efficient cores only | 40.9 | 23.4 | 59.2 |
| low power cores only | 35.2 | 34.4 | 36.0 |
| free | 26.5 | 14.0 | 60.6 |
| free, EcoQoS forced on | 57.5 | 50.8 | 64.2 |
| free, EcoQoS forced off | 15.2 | 13.8 | 16.8 |

Without the fix the speed flips between two states with nothing else changing, for minutes at a time:

| Run | Intervals | Min | Median | Max | Share above 30 |
|---|---|---|---|---|---|
| 30 min stream | 884 | 12.8 | 24.4 | 65.4 | 46 % |
| 15 min stream with writes | 441 | 13.3 | 45.5 | 77.2 | 84 % |
| 17 probes | 1048 | 10.0 | 10.8 | 52.4 | 8 % |
| with the fix, 2 min stream | 59 | 13.3 | 14.0 | 14.8 | 0 % |

In the 30 min run, slow from 640 to 1190 s; speed against the load on the performance cores: correlation -0.96 (per 90 s). The
max of 77.2 is the range of the merge runs (47 to 78). The merge runs themselves were not logged this way, so that link is a match
of numbers, not a replay.

Fix: `tools/mdb_serial.py` line 64 `full_speed(job)`, called at line 133 after `Program succeeded`. It lists the processes of the
existing job object and sets `ProcessPowerThrottling` to control execution speed, state off, for each (2 processes). Start-up fell
from 29 to 31 s to 23.7 s. If the job or the call fails, the port works as before. Windows only, as the rest of that code.

Side effects: the simulator is now reliably near 14 (10.9 with little stream traffic). The largest heartbeat gap, 6.7 s of wall clock,
is 480 ms of target time at 14 and 620 ms at 10.9; the target allows 1000 ms. `capture_time_scale = 100` now waits about 7 times too long.

## A, C: what was excluded

No gap over 2 s in the sample index: 30 min stream (74389 samples, 0 lost, 0 resync), 15 min with writes at the probe rate (a write
every 5 s, a value write every 15 s, 24467 samples, 0 lost), 17 runs of the real `tune_api.probe` on one MDB (102 probe writes, all
seen, all `ok`). This was without the fix, in both speed states. All of this ran outside the GUI; the event was in a GUI session.
At a rate of 1 in 10, 17 clean probes still happen 17 % of the time, so this does not show the event is gone.

| Suspect | Measured |
|---|---|
| Simulator stops | Stopwatch advanced in every interval |
| Output buffered | File grows in steps of 1 to 7 bytes, polled at 10 ms, largest pause 22 ms. Stopwatch minus sample index stays within 80 ms of target time |
| Java GC | Parallel GC, heap limit 8.4 GB, 318 MB in use. 30 min: 3460 safepoints, 9.6 s in total, largest 0.50 s, 3 full collections. Allocation about 500 MB/s |
| `write` blocks | stdin write at most 2 ms; next MDB answer median 3 ms, at most 24 ms, during a stream. A value write takes 1 s in `MdbSerial.write`, by design |
| 32 bit write hits the neighbour of `sim_rx_len` | `n_ch` 4 and `mode` 0 after all 166 checked writes |
| Disk on the file | The file is in the local temp folder. Largest read 0.20 s. Other background software on this PC cannot be seen from here |
| Standby | Kept awake during the runs. For A, the Windows log has no event 506 |

Not excluded for A: the GUI process itself stalling, because `_s_wait` compares the wall clock and would fire before a starved reader
thread catches up; a firmware or TX stop that only arises in a GUI session. The watcher that would show this (firmware state through
`Print` during a gap) never had a gap to look at.

## D

NiceGUI derives `ping_interval` 4 s and `ping_timeout` 2 s from `reconnect_timeout` 3 s (`nicegui.py` lines 138 and 139). A pong later
than 2 s closes the socket on the next send, and the content goes after 3 s more. So the "2.6 s" of card 4.4 was over this limit.

A lag probe, loaded from outside, ran through one `test_gui_mdb.py` (5 GUI processes): during runs the event loop was at most 0.58 s
late, no pong was later than 0.5 s, every socket close was `transport close` from the test. Longer lags: about 1 s during start-up
imports, and 18.5 s in the 8 s wait of the shutdown hook, where a closing GUI is expected to block. The fix was in place. No cause
shown, so `reconnect_timeout` is unchanged.

## Follow-up

Decisions: the simulator is fast with `full_speed()`, so `capture_time_scale` is removed and the wall clock is scaled by the port
(`time_scale`, 25 on MDB) in every wait without a stream. The run must show whether the fix took effect.

Changes:

- `capture_time_scale` removed from `tools/mdb_serial.py`, `Scope` in `gui/scope_gui.py`, `gui/tune_api.py` (docstring, session
  attribute, `wait_target` is back to `time_scale`), the check in `tests/test_protocol.py` and the test `capture_scales` with its
  port in `tests/test_script.py`. No mention is left outside the evidence of 6.1 and the earlier cards.
- `MdbSerial.throttling_off` keeps the return value of `full_speed()`. The port line of `run.txt` ends with
  `power throttling off for n processes`, only for a port that has the attribute. With n = 0 a line
  `warning: power throttling of the simulator is not turned off, it may run up to 4 times slower` follows. Warning only.
  Test `throttling_line` in `tests/test_script.py` (fake port with 2 and with 0 processes, and a port without the attribute).
  `tools/report.py` is not touched: its run report format has no port line of this kind.
- `tests/test_gui_mdb.py`, `start_run()`: the second Run is pressed only for E401 or for a stream stop of the probe (`during the
  probe` in `run.txt`), with a NOTE. The test ends with `retries: n`. Everything else fails at once, a differing result is never repeated.
- `SIMULATOR.md`: the UART file grows 1 to 7 bytes at a time (largest pause 22 ms), not in blocks; a paragraph on power
  throttling, `full_speed()`, the measured speeds, Modern Standby and the unknown causes of A, C and D.
