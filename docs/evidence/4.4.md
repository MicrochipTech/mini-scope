```

.venv\Scripts\python tests\test_gui.py              (once at the end: 120 OK, 0 FAIL)
```

The test drives the real GUI (`scope_gui.py --mdb <sim ELF>`, headless Edge, helpers imported from `test_gui.py`). Every wait
is an event (page state, a line in run.txt, a process that is gone) with a timeout derived from `MdbSerial.time_scale` (25),
`tune_api.PORT_TIMEOUT_S` and `script_tab.GRACE_S`. Every 2 s `wait_end` also looks at the socket of the page and at run.txt, and
fails at once when the run ended and the page was not told. The processes of each part (GUI, cmd, Java) are recorded by PID
and must be gone at the end; leftovers are ended by PID and count as a failure. An MDB that was not started by the test makes
it stop without touching it.

## What went wrong on the way (test and GUI)

- Write field select: the item text has one space after the name (`motor.run (0x...`), the first version looked for two.
- The Abort button is in the Script tab; the tab switch must wait for the tab (a null element in the page).
- `close`: a new page after a finished run says "not connected" while the GUI still holds the port (existing behaviour, listed
  in 4.2). The test no longer expects Run to be enabled there, and the GUI-close part is its own session (`guiclose`).
- `lost`: the check "no process left" was run with the GUI recorded as one of the processes, but the GUI was still up. It looks
  at java.exe and cmd.exe only at that point.
- The process table was read in the console code page and failed on a byte of a command line in one run; it is read as UTF-8 now.
- **"no browser page for 5 s" in an earlier run.** In two of about eight sessions the page vanished while a full run was under
  way: the run was aborted by the 5 s rule, the page showed nothing for the rest, and the test waited for its (long) timeout.
  The page was gone by itself, nobody closed it; the rule did what it is built for. The cause of the loss is not found. The GUI
  log held no error for it, the answer time of the GUI to page requests was at most 2.6 s in all later runs, and the situation
  did not return in the final two runs. The test now fails within seconds when the run ended but the page was not told, prints
  every websocket close, navigation, crash and console error of the pages, and keeps its temp folder on a failure. Not
  reproduced, so not fixed: it stays a finding. One run of the final code would show it again.
- **GUI closed, run.txt without a result line.** The first version of the test required the read-back. The abort writes the safe
  value at once, but the read-back through MDB needs about 30 s (the abort of item 2 took 28 to 37 s), and the GUI waits 8 s
  for a run on shutdown, then closes the port. The process was gone before the run could finish, so `aborted: GUI closed` is the
  last line and `result` and the read-back are missing. On a real port the read-back takes milliseconds. The test reports
  whether the read-back was reached and does not require it on MDB. Whether the safe value reached the target before the
  simulator was closed cannot be shown on MDB.
- **Real bug found on the way, fixed (commit b5f0c19):** the shutdown hook `script_tab.shutdown(wait_s=8.0)` was registered
  with `app.on_shutdown`. NiceGUI passes the app to a handler with one parameter, so `wait_s` became the app object and
  `time.monotonic() + app` raised a TypeError before any abort ("Application shutdown failed" in the GUI log). Only the
  console hook (Ctrl+Break, closed window) did the abort so far, a graceful stop of the server (Ctrl+C in the terminal) did
  not. New `script_tab.on_app_shutdown()` without parameters is registered. Regression check `test_gui.py hook`: calls the hook
  the way NiceGUI does; the old function fails that check, the new one passes. After the fix the GUI process needs 23 s to end
  when closed in a run on MDB (8 s wait, then the port closes); before, 4.2 s.
- In one session the first Run after a Scope stream ended with `E401 the target does not answer the ping` (the probe does not
  repeat a ping). A direct test of ping during a stop on MDB (6 delays between 0.2 s and 5 s) answered every time, so a race
  with the stop is not shown. The simulator is known to lose a mailbox write now and then (SIMULATOR.md). The test presses Run
  a second time once in this case and prints a NOTE; 0 repeats in the two final runs. Open: if it happens on a real port the
  probe should try the ping a second time.

## Standby

A run in the second half of the morning was cut by the PC: Modern Standby by idle timeout from 08:53 to 09:11 (717 s gap in the run
log, "stream stopped: no sample for 500 ms" after the wake-up). The safe end worked after it, with the safe value read back. That run
is not counted. The two final runs ran with the display and the system kept awake and did not see it again. Standby is a cause of
stream stops that SCRIPTING.md or TROUBLESHOOTING.md should name (M7.1): a laptop that goes to sleep during a run aborts it.

## Not tested

- Hardware: nothing here says anything about a real board. MDB runs 14 to 25 times slower than real time; timing, pins and the
  clock are not tested. The slow read-back on MDB hides how fast the GUI-close path is on a real port.
- Other browsers than Edge. Ctrl+C itself (the repaired hook is tested by the NiceGUI call pattern, not by a signal; Ctrl+Break is).
- A closed console window (same handler as Ctrl+Break).
- A loss of the page that cannot be reproduced (above).
- The abort during a capture run (`tune_current.py`) on MDB.
