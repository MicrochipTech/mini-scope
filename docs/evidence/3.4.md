# Card 3.4: run_script, tune_startup, simulator cleanup, script cursor

## A. Simulator left running (tools/mdb_serial.py)

`MdbSerial.close()` now ends the process tree it started: polite `Halt` and `Quit`, then
`taskkill /T /F /PID <pid of cmd>`, then `TerminateJobObject` on a job object. The job object has
`KILL_ON_JOB_CLOSE`, is made with ctypes, and holds the `cmd` process (and so the Java child), so the
simulator also dies when the Python process is killed hard. `atexit` calls `close()` as well. Nothing is
killed by image name.

    .venv\Scripts\python tests\test_mdb_close.py

The test records the PIDs below `cmd` while MDB runs, then checks that none of them exist 5 s after the end.
Three cases: normal close, close while MDB ignores `Halt`/`Quit` (hung), caller killed with
`taskkill /F /PID` (no `/T`).

| case | old code | new code |
|---|---|---|
| close | no process left | no process left |
| hung | 1 process left | none left |
| caller killed | 2 processes left | none left |

Old code: `FAILED`, left-over PIDs ended by the test. New code: `all passed`.

## B. Script cursor (gui/tune_api.py)

The script sees the stream at a cursor in sample indices (see the module docstring). `wait_ms(n)` moves it
by exactly n, `read()` gives the value at the cursor, `write()` sets it to the newest sample plus the output
lag, `trace_begin()`/`trace_end()` use it. Monitor, `limit()`, heartbeat and stall check use the newest sample.

    .venv\Scripts\python tests\test_script.py cursor cursor_read

`tune_startup.py` time_ms for ramps 50, 100, 200 (model: 221, 161, 131, `docs/evidence/m1/model_check.txt`):

|---|---|---|---|
| before (old code, SIM, 5 runs) | 150, 150, 150, 160, 170 | 120, 120, 110, 120, 130 | 100, 100, 110, 80, 110 |
| after, SIM, 5 runs | 230, 230, 240, 230, 230 | 170, 180, 170, 170, 170 | 140, 140, 150, 140, 150 |
| after, 200 ms bursts, 3 runs | 230, 230, 240 | 180, 180, 190 | 150, 150, 160 |

Not met as briefed: the brief asked for within 10 ms of the model. The values are 9 to 29 ms above it.
Reason: the model runs on the wall clock, so a write takes effect somewhere between the newest sample the script

accepts -10 to +20 ms around the model without bursts. With bursts the time of a write is known to one chunk only,
see "Supervisor review". The step in `cursor_read` (closed loop
seen at cursor step 16 of 40) is identical with and without bursts.

## Supervisor review

Two causes explain the differences between ports.

1. Cursor taken before the write returned. `write()` took the newest sample before `scope.write`. The MDB port
   sleeps up to 1 s wall clock inside `write`, which is many target ms, so the cursor lagged by that time. Fix:
   the cursor is set after the write has returned (`_drain()`, then the newest sample).
2. Chunked delivery. On a port that delivers in chunks the PC knows the time of a write only to one chunk, so a
   start time can be off by up to the chunk. The honest limit is: right to one poll step (10 ms) or one chunk,
   whichever is larger. Test limit with 200 ms bursts: model + chunk + 30 ms for each row and for the comparison
   with the plain run. `good_starts` stays exact. The claim in part B that bursts and no bursts agree within 20 ms
   is withdrawn: run 7 of 10 gave time_ms 300 for model 131.

target time, 9 traces and `tuning.h`):
