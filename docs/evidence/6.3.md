## Error table: how it was generated

`gen63.py` (kept in the scratch folder, not in the repo) imports `gui/tune_check.py`, takes
`RULES` (68 codes), holds a dict of advice texts with one entry per code, and stops with an
assertion if the two key sets differ. It writes `| code | stage | meaning | what to do |`
rows into `SCRIPTING.md` in place of a marker, sorted by stage, errors before warnings. The
meaning column is the text of `RULES` with the first letter in upper case. Result:
`68 codes 68 rows`. A new rule in `RULES` makes the generator fail until it has an advice text.

## Where the code and the plan differ

1. The plan says (M6) the note on Hall sensors is "with Hall sensors the startup sweep only
   covers the start current". The code has no Hall support at all and `tune_startup.py` does
   not know the sensor type. The sentence in SCRIPTING.md section 8 is the plan's note with
   advice (remove the ramp), not something the code checks.
2. The plan says "`limit()` is only partly supervised during the probe" only via DECISIONS
   3.3b; the plan text of "Script errors" does not say it. SCRIPTING.md states it as in the
   DECISIONS line.
3. The plan lists E-codes only by example; the real set is 68 codes (stages 1 to 4). The table
   follows the code.
4. Not a disagreement but worth knowing: after a run, `tune_block_ms()` stays at 1 until
   `tune_alive` changes again or the firmware is reset, because the PC stops the heartbeat.
   The plan does not say this; SCRIPTING.md section 6 does.
