## What changed

- `gui/tune_api.py`, event fields only: the `row` event carries `row_traces`, the indices of the traces recorded since the
  previous `row()` (the same traces that `_tuning_refused` counts as "after the last row"). Documented in the docstring.
- `gui/script_tab.py`:
  - `RunState` keeps `columns`, `table_rows` (values, invalid, trace indices), `trace_meta` (every trace: title, file, flags,
    sample count, time unit) and `trace_data` (the samples), plus `mark` and `summary_chan` from the result.
  - Comparison table (`table_view`): a row per `row()` as it arrives, columns `#` (arrival order), the columns of `table()`,
    `status` (`ok`, or `failed`, `invalid`, `unfinished`, from the row's traces and the row's own `invalid`). Every column sorts
    (Quasar sort, numbers as numbers). Failed and invalid rows have red text, the `summary_mark` row (first row with a cell equal
    to the mark, same comparison as the summary picture) is yellow and bold, selected rows blue.
  - A click on a row toggles it. The overlay chart (`overlay_series`) shows the traces of all selected rows for one channel
    (selection list, default the `summary_channel()`), from trace start, physical value = raw x factor of the `channels` event,
    axis named `<channel> [<unit>]` (`(raw)` without unit), failed and invalid traces dashed, the marked row's traces thicker.
    Series names are `NNN title` plus `(failed)` etc., as in the summary picture.
  - Time axis: the array is `time_ms` (or `time`, if an event has that name instead) and the label comes from the event field
    `time_unit`, default `ms`. So the capture traces of card 6.1 work if they send `time_unit`.
  - No `table()`: the table lists the traces (`trace`, `samples`, `status`) and the overlay works the same.
  - Traces that belong to no row (the confirm runs after the last `row()`) are counted in a line below the table.
  - Export tuning.h: enabled only if the result has `tuning_h` and no run is active; copy through `pick_file(save=True)`;
    the environment variable `MS_EXPORT_PATH` replaces the dialog (tests).
  - Report: runs `tools/report.py` as a subprocess (`--out`, `--doctor`, `--hw`, `--run` in the project folder, or in
    `MS_REPORT_DIR`, used by the test), then shows the path and the text of `mini-scope_report.txt` in a dialog with the
    sentence that nothing was sent. Disabled during a run.
  - The summary picture is now directly below the table and the overlay.
- Live chart of the Scope tab: no change needed, 4.2 already scaled by the `channels` event factors and put `[unit]` into the
  series names (the legend). Only display uses the factor: `scope_gui.factors()` is read by the chart, the CSV and the PNG;

## Memory

The 'trace' event holds arrays of `Scope.snapshot()`; the session keeps its own copy of every trace. `RunState` copies the arrays
it keeps (an event array can be a view of the whole stream) and keeps at most `KEEP_TRACES = 200` traces, and at most 256 MB
of samples (`KEEP_BYTES`, the oldest go first; one trace can hold up to 200000 samples, so 200 long traces would be about 1.6 GB).
The meta data of all traces stays (a few hundred bytes each). A trace that is out of memory is named in the overlay note with
its `trace_NNN.csv`; its row in the table stays. A trace of the example run has about 350 samples x 5 arrays x 8 bytes = 14 KB;
with 4 channels and 2000 samples a trace is 80 KB, 200 of them 16 MB. Test of the limit with the class itself: 250 traces of
2000 samples, 2 channels, give `len(trace_data) = 200`, oldest kept index 51, 250 meta entries, 9.6 MB; five traces of 200000
samples and 4 channels are all kept (40 MB). Nothing else is bounded: the table rows are small.
`begin()` of the next run clears all of it.
