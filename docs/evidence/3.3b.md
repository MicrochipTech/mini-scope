## Interface

```
tune_api.probe(script_path, scope, table, on_event=None, out_dir=None, elf_name=None, hooks=None) -> result dict
```

Blocks until the probe and the safe end are done. `abort()` works from another thread. Raises `RunRefused` like
`run()` (stages 1 to 3 with errors, run active): nothing reached the target. `out_dir=None` keeps no run folder
(`run.txt` goes to a temporary folder that is removed, `result['folder']` is `None`).

`run()` is still non-blocking. Its script thread now does: execute the script body once, state `probe`, the probe,
`main()` in the same namespace. `hooks={'skip_probe': True}` leaves the probe out (used by the small tests).

Events: new state `probe` (`starting`, `probe`, `trial`, `running`, `safe_end`, `done`), new event
`{'type': 'variables', 'rows': [{'name', 'role', 'address', 'type', 'value'}]}`. `role` is a list of `measured`,
`written`, `safe`, `limit`, `idle` (read in `check_idle()`), joined by `, `; `value` is raw. The result of `run()` and
`probe()` has two new keys: `rows` (the same list) and `problems` (stage 4 problems as `file:line: severity: text [code]`).
`rule_codes` carries the stage 4 codes as counts, nothing else.

## Stage 4 codes (RULES in `gui/tune_check.py`)

| Code | Meaning |
|---|---|
| E401 | no answer to the ping (text names TROUBLESHOOTING.md section 4) |
| E402 | `build_id_check` refused |
| E403 | variables cannot be streamed |
| E404 | heartbeat cannot be written |
| E410 | `expect()` in `check_idle()` is false, at the line of the `expect()` call, with its text |
| E411 | exception in `check_idle()`, at its line (also `read()` of a name the probe did not read, more than 10000 reads) |
| E412 | `check_idle()` touches the target (`write()`, `stream_start()`) |
| E420 | a written variable does not show the new value, or does not hold it for 100 ms: the firmware overwrites it |
| E421 | a changed variable could not be restored |
| E422 | write test impossible (write refused, too many samples lost) |
| W401 | write test skipped, `allow()` has one value |
| W402 | write test skipped, current value outside `allow()` and no neighbour inside |

Problems without a script line (E401, E402, E404) are reported at line 1.

## Order of the steps and the safety rules

1. `tune_check.record()` of the script gives the declarations (channels, allow, safe, limit) and the names read by
   `check_idle()`. Errors in stages 1 to 3 refuse the probe.
2. Ping. Nothing is written before it. No answer: E401, no safe values (the log says so).
3. `build_id_check`. Then `Session.verified = True`: every end writes the safe values (the condition of the safe end is
   now `started or verified`). A port that fails in step 2 or 3 writes nothing.
4. Heartbeat thread starts, one per session. `stream_start()` finds it running. The probe waits for the first write and
   50 ms target time before it reads anything. The heartbeat writes once at once when the stream of the run begins, so
   the change from wall clock to sample timing leaves no gap.
5. Live values: all names (channels, allow, safe, limit, idle reads), short streams of at most 4 variables. `variables` event.
6. `check_idle()` of the real script, `read()` answers from step 5. `write()` and `stream_start()` raise `IdleRefused`
   (E412), `wait_ms()` returns at once, a name the probe did not read is E411.
7. Write test, only if `check_idle()` passed: per allowed variable without `safe_value()` one stream with the variable
   and up to 3 limit variables. First sample is the original value. New value is +1, or -1 if +1 is outside `allow()`.
   The write is entered in `Session.pending` inside the gate before it is sent. The hold starts at the first sample that
   shows the new value (samples already on the line show the old one), it must stay for 100 ms target time. Then the
   original is written and read back (must show and hold for 2 samples), one rewrite, then E421. All writes go into
   `run.txt` as `write <ms> ms <name> = <value> (probe)`.
8. Stand-alone: the probe ends with `request('end')`, the safe end runs, the heartbeat stops. In a run the heartbeat
   continues into the stream.

Restore on every abnormal end: `_send_safe` puts the `pending` originals in front of the safe values in the same write
message (applied in order, so before them), `_verify_restore` reads them back after the safe values. A variable that cannot
be restored is an error in the log with both values (`startup.ramp_rate was changed from 100 to 101 by the write test and
could not be restored: ...`), so the result is `error` or `aborted` with `errors` set, and no run starts (the probe ends the session).

## What is supervised during the probe

`limit()` is checked on what is in the running short stream, nothing else. Step 5: the group of at most 4 variables,
one group after the other, so a limit variable is only watched while its own group streams (a few ms). Step 6: nothing
streams, the values are frozen. Step 7: the written variable plus up to 3 limit variables; a fourth and further limit
variable is not watched during that variable's test. The monitor thread supervises nothing during the probe, only the
stall and port checks of the probe's own wait loop (500 ms target time without a sample, dead reader) apply. A limit
variable in the current group trips it (test `limit`). This is looser than in the run itself, the probe is meant to be
used at standstill with the power stage off.

## Deviations and findings

- The script body runs in three places per probe or run: the dry run of stage 3 (fake API), the dry run of `record()`
  inside the probe, and once in the real session. The probe and `main()` share that one real execution (same namespace),
  so module level code runs once on the real API. A module level side effect such as writing a file happens three times
  (test `idle` counts 3; it was 2 before). To avoid the second dry run `check_script` would have to return its recording;
  that is outside the files of this card.
- The restore writes the value the variable had. If that lies outside `allow()` (it came from the firmware), it is still
  written, as it is the firmware's own value. The new value is always inside `allow()`.
- Detection of a variable that is overwritten: E420 also when the new value never shows within 50 ms (a model that overwrites
  every 100 us may never show it to a 1 ms sample). A firmware that overwrites it more slowly than 100 ms is not found.
- The heartbeat writes once more than before when the stream of a run begins (one write at the change to sample timing).
- Stand-alone probe: the safe values go out at its end (target verified), and the heartbeat stops, so 1 s later the target
  latches fault 5 again until the next heartbeat.
- `results.csv` is not created for a stand-alone probe.
