# Card 2.1: Scope and port changes (plan M2)

## Changes

- `Scope`: `resyncs` counter next to `lost` (reset in `start()`), counted once per bad sync byte in
  `_stream`. `wlock` around every `ser.write` (`_send`), `write_many(writes)` builds all `W` commands
  first, sends nothing if one is invalid, and sends the rest in one `ser.write`. `write()` is
  `write_many` with one entry. Properties `time_scale` and `output_lag_ms` read the port with
  `getattr` (defaults 1 and 0).
- `SimSerial`: `RLock` around `_advance`, `sim_rx`, and every access to `buf`. Attributes
  `time_scale = 1`, `output_lag_ms = 0`.
- `MdbSerial`: `time_scale = 25`, `output_lag_ms = 3` (class attributes, as `quiet`).
- `hw_check.py`: `resyncs` shown in the stream lines (one line).
- `Scope.write()` does not yet wait for the output lag. The attributes are only there; the waiting
  belongs to the script API card.

## Locking, by reading the code

- The reader threads (`_stream`, `_capture`) never take `wlock`, and `SimSerial` holds its lock
  only for one `_advance` or one `sim_rx`, never while sleeping. `MdbSerial.read` takes no lock.
  So a writer that sleeps (up to 1 s per 60 byte chunk in `MdbSerial.write`) cannot starve a reader.
- `stop()` clears `running`, joins the reader, and only then writes `S`. The reader may wait for
  `wlock` in auto capture (`R`), but a writer holds `wlock` only for one `ser.write`, so the join
  ends after the sleep. No lock is held while waiting for another one: no cycle.
- Checked by test (below): reader delivers samples while a write sleeps 1 s, `stop()` returns.

## MDB: write_many with mdb_serial

Build as in `start_sim.bat` (`make -f Makefile CONF=sim build`, up to date). Script: `Scope(MdbSerial)`,
stream of `startup.ramp_rate`, `align_current`, `handover_speed` (u16) at 1000 us, then
`write_many` of 111, 222, 333.

```
start-up 24 s, time_scale 25, output_lag_ms 3
ping True
start None
before [100, 400, 600]
write_many returned None after 0.50 s
values in the stream after 0.20 s: [111, 222, 333] (wanted [111, 222, 333])
lost 0 resyncs 0
```

The 3 writes are 24 bytes, one mailbox chunk. `write_many` took 0.50 s (wall clock) and all 3 values
showed up in the stream 0.20 s after it returned, once. One run only.
