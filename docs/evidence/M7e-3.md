# M7e-3: a message instead of a traceback when the simulated target never answers

Finding F4 of M7e: a dead TX path (nokick) or a firmware that hangs before `scope_init()` ended `hw_check.py` and
`run_script.py` in a bare `TimeoutError` traceback after about 108 s.

## Changes
- `tools/mdb_serial.py`: new `MdbNoAnswer(TimeoutError)`. The start-up now raises it with
  "the firmware in the simulator sent nothing within 90 s: it may hang before scope_init(), the TX path may be dead
  (no tx_kick), or the ELF is not a sim build. See SIMULATOR.md section 9 and TROUBLESHOOTING.md section 4.2".
  `_wait_for` raises it as "the simulator did not report "<text>" within <n> s: MPLAB X may be missing or in another
  place, an old MDB process may block it, or the ELF could not be loaded. See SIMULATOR.md section 9".
  Both call `close()` first, so the Java process does not stay behind.
- `tools/hw_check.py` `connect()`: `except TimeoutError` next to the `SerialException` one: FAIL line `ping` with
  the hint `TROUBLESHOOTING.md 4.2, SIMULATOR.md 9`; the report file holds `simulator did not answer`.
- `tools/run_script.py`: `open_scope()` turns it into `NoPort`; `main()` prints `ERROR: <message>`, writes the report
  (`status error`, `reason simulator did not answer`) and exits 1.
- GUI Connect (`gui/scope_gui.py`): unchanged. The handler already catches `Exception` and shows `Error: <message>`
  in the status line, so the new text appears there; the button is re-enabled by `set_connected`. Not run in a GUI.
- Docs: `SIMULATOR.md` section 9 table (two rows), `TROUBLESHOOTING.md` 4.2 (one bullet).
- Test: `tests/test_mdb_noanswer.py`.

## Real COM port (not changed)
`hw_check.connect()` with no byte: "no byte at all from the target at any baud rate", hint "wiring, PICkit still
connected, debug build, firmware not running: TROUBLESHOOTING.md 1, 4.1, 4.2 (run with --loopback to check the
adapter)". With stray bytes: "noise or a wrong clock far off", hint 4.3, 4.4. Causes are named.
