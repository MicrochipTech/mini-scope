# Card 5.1: tune_block.h and the ELF check

## What changed

- `firmware/tune_block.h` (new): `tune_alive`, `tune_build_id`, the text `tune_build` (`__DATE__ " " __TIME__`),
  `tune_block_init()` (once at start, before the interrupts: `tune_build_id = tune_crc16(tune_build)`) and
  `tune_block_ms()` (every 1 ms, returns 1 while the heartbeat is lost). No motor names in it.
- `firmware/tune_model.h` includes it and has no heartbeat code of its own. Same behaviour: armed by the first change of

  `current_ref = 0`, fault 5).
- `firmware/example_main.c` includes `tune_block.h` and calls `tune_block_init()` first in `main()`.
- `tests/mock/sim.c`: `tune_alive` and `tune_build_id` are macros on `mock_ram` (0x1128, 0x112A), `tune_block.h`
  then defines no variable of that name. The text is the C string of the header; `sim_build()` and `sim_crc16()` export
  it for the tests.
- `gui/elf_vars.py`: `VarTable.read_string(name)`; `from_symbols(..., strings=)` for the name tables.
- `gui/tune_api.py`: `build_id(text)` (the CRC in Python) and `build_id_check(session)`.
- `tests/sim_serial.py`: `SYMBOLS` is a `dict` with an attribute `strings` (the text of the DLL), so every table made by
  `VarTable.from_symbols(SYMBOLS, SYMBOL_TYPES)` has the text; `tune_build_id` is in the table.

## How the text lies in the ELF

Built as `start_sim.bat` does (`make -f Makefile CONF=sim build`, XC-DSC 3.30, DFP 1.10.386), read with pyelftools:

    section .const  sh_addr 0x8436  sh_size 0xb4 (180 bytes in the file)  flags ALLOC (not WRITE, not EXEC)
    segment PT_LOAD vaddr 0x8436    paddr 0x436    filesz 0xb4
    symbol  _tune_build  0x8436  size 21        map file: .const 0x8436, 0x5a bytes, load address 0x000436
    first bytes of the section: 4e 6f 00 00  76 20 00 00  20 31 00 00  20 32 00 00 ...   = "No" "v " " 1" " 2" ...

- `const` data is in `.const` at its address in data space (the program space visibility window, 0x8000 and up). The
  DWARF location of `tune_build` is that address.
- The file holds one 24 bit program word as 4 bytes. The two low bytes are two data bytes, the other two are zero (high
  byte and phantom byte). The section is 0xb4 bytes in the file and 0x5a data bytes in the map: half.
- So the data byte at address `a` is file byte `4 * ((a - sh_addr) // 2) + (a - sh_addr) % 2` of the section.
  `read_string()` takes sections that are ALLOC and not WRITE (flash) and that contain the whole array. `.data` and
  `.ndata` (RAM, one byte per byte) are excluded: a text in RAM gives `not_string`. The same layout is used for a
  section at a program address below 0x8000 (`space(prog)`): not built, not tested.
- Result: `tune_build` read from the ELF is `'Nov  1 2026 13:14:32'` (20 characters, the array has 21 with the zero).

Confirmed against the firmware in MDB, not only by reading: the firmware computes `tune_build_id` from the string that it
reads through the data space pointer at start, and the value equals the CRC of the string read from the ELF. Two
builds, one after the other:

| ELF | text in the ELF | CRC in Python | `tune_build_id` in MDB |
|---|---|---|---|
| first | `Nov  1 2026 13:14:32` | 0xC595 | equal: the probe passed (run below) |
| second | `Nov  1 2026 13:26:35` | 0xB6C8 | 0xB6C8 (shown in the refusal text) |

## Checksum

CRC-16/CCITT-FALSE: start 0xFFFF, polynomial 0x1021, no reflection, bitwise, 8 shifts per byte, in `tune_crc16()` (12
lines). Check value of `"123456789"`: 0x29B1, C and Python. Compared by `tests/test_block.py`:

- C (sim.dll, the real header) against Python on 306 texts (check value, empty, 6 date strings, 300 random of 1 to 40
  characters): 0 differences, 304 different texts give 304 different ids.
- All 18 swaps of two different neighbours of the build text change the id, all 160 single bit changes change it. The
  same 18 swaps leave a plain byte sum unchanged.
- Start cost: 20 characters times 8 shifts, a few hundred cycles (an estimate from the loop, not measured).

## The check

`build_id_check(session)` (`gui/tune_api.py`), in this order: read the text of the ELF (`read_string('tune_build')`),
look up `tune_build_id` (16 bit), stream it for 3 samples (read only, a short stream like the ones of the probe),
compare with the CRC of the text. Everything else refuses with E402 and a text that ends with "program the matching
build, or select the ELF that belongs to the programmed one (add firmware/tune_block.h if tune_build_id is missing)":

- text not in the ELF, not an array of char, ELF without debug information: refused
- `tune_build_id` missing or not 16 bit: refused
- values differ: refused, the text shows both values and the text from the ELF
- A name table without the text (plain addresses, no ELF): refused the same way. There is no run without the check: the
  safety rule says the ELF must be verified before the first write, and without the text nothing verifies it.

Where it runs: the probe, step 3, right after the ping (`_probe_steps`). `Session.verified` is set after it passes.
`_refusal()` (stream_start) runs it only when `verified` is false, that is when the probe was skipped; then it also counts
E402 in `rule_codes`. A normal run reads the id once. Nothing is written before the check in either path; the stream of
the check is read only.

Hook `skip_build_id` (for the small tests only, `tests/test_script.py` `go()`): `build_id_check` returns None. `run_script.py`,
the GUI and `test_probe.py` do not set it.

## Notes for SCRIPTING.md

- `tune_build` changes only when the file that includes `tune_block.h` is compiled again. A change in another file does
  not move it, and then an old ELF with the same text is not noticed. Put the block in a file that changes, or build clean.
- The id proves the build, not each address in it: the other variables are resolved from the same ELF, which is the
  one that was proved.
