# M0: risk check in the simulator

All numbers come from MPLAB X v6.35 MDB, dsPIC33CK64MC103, configuration `sim`, Timer1
as mini-scope's sample clock, 115200 baud, FP = FCY = 32 MHz. Simulation only: nothing
here says anything about hardware.

The firmware is built from a scratch copy in the temp folder with `docs/evidence/m0/m0_load.h`
added. Worktree firmware is unchanged. Commands, run from the repository root:

```
python docs/evidence/m0/m0_stream.py --fast 2 --secs 300
python docs/evidence/m0/m0_stream.py --fast 0 --secs 120
python docs/evidence/m0/m0_stream.py --fast 1 --secs 120
python docs/evidence/m0/m0_stream.py --fast 2 --kick --secs 120
python docs/evidence/m0/m0_lag.py --fast 2 -n 10
python docs/evidence/m0/m0_lag.py --fast 2 --kick -n 10
python docs/evidence/m0/m0_rx.py
```

`--fast`: 0 no extra timer, 1 SCCP1 interrupt at 10 kHz that only counts, 2 the same with
a control body of 25 fixed point multiplications and 6 saturations. `--kick`: the 10 kHz
interrupt also sets `_U1TXIF`. Target time comes from the MDB `Stopwatch` command read while
running. It counts instruction cycles, so seconds = cycles / 32e6. The seconds it prints
itself assume 64 MHz per cycle and are wrong by a factor of 2. Checked: 3420 ticks of the
10 kHz timer against 10943776 cycles is 0.342 s in both.

## Results

| Result | Value |
|---|---|
| 1. second timer | runs: SCCP1 at 10 kHz next to Timer1 at 1 kHz, 10 ticks per sample in every sample |
| 2. stream 4 x 16 bit, 1 ms | stable, no stall in 20694 samples; 10.00 % lost without kick, 0 with kick |
| 3. slowdown | 14.45 with realistic load (range 14.2 to 15.0), 12.51 without 10 kHz interrupt |
| 4. output lag, target time | 57 / 58 / 59 ms without kick, 2 / 3 / 3 ms with kick (min / median / max) |
| 5. UxRX_ISR with injected data | yes, with SCL `packetin`; full configure and run works |

Values for the design:

- `time_scale`: 14.5 measured, 15 is the rounded value for this load. Depends on the PC.
- Output lag: 58 ms target time (0.8 s wall) without kick, 3 ms (0.1 s wall) with kick.
- Sweep point: a 0.4 s target time start takes 0.4 x 14.5 = 5.8 s wall, plus the lag. A
  single stream of 20.7 s target time (300 s wall) ran without a stall.

## 1. Second timer

mini-scope uses Timer1 in `sim` (default `SCOPE_TIMER`), so the candidate is SCCP1 in 16 bit
timer mode, period 3200 FP, priority 3 (above mini-scope). SCCP2 runs free at FP/4 as an
independent time base and is streamed as a channel, 8000 ticks = 1 ms.

| Run | wall | fast ticks per sample | SCCP2 ticks per sample | SCCP1 from `fast_total` / Stopwatch | ISR length |
|---|---|---|---|---|---|
| fast 2 | 300 s | 10 / 10, mean 10.0000 | 7999 / 8001, mean 8000.00 | 9999.18 Hz | 1136 cycles, 35.5 % of 100 us |
| fast 1 | 120 s | 10 / 10, mean 10.0000 | 7999 / 8001, mean 8000.00 | 9998.09 Hz | 12 cycles |
| fast 2, kick | 120 s | 10 / 10, mean 10.0000 | 8000 / 8000, mean 8000.00 | 9998.14 Hz | 1136 cycles |

Timer1 is therefore 1000.0 Hz and SCCP1 10000 Hz. The Hz figures from `fast_total` are slightly
low because the Stopwatch starts before the timer does. The fallback in the main loop is not needed
and was not tried.

## 2. Stream

Channels: 4 u16, 1000 us, frame 10 bytes. Counts from the sequence byte.

| Run | samples | received | lost | lost after sample 3000 | `scope_overflows` |
|---|---|---|---|---|---|
| fast 2 | 20694 | 18673 | 2021 (9.77 %) | 10.00 % | 2026 |
| fast 0 | 9551 | 8645 | 906 (9.49 %) | 10.00 % | 912 |
| fast 1 | 8019 | 7266 | 753 (9.39 %) | 10.00 % | 759 |
| fast 2, kick | 8488 | 8488 | 0 | 0.00 % | 0 |

Without kick every loss is a gap of exactly one sample (distance 2: 2021 times, nothing wider).
Bad bytes were 1 to 5, within one frame length, from the first alignment on the running stream.

Cause, inferred from the numbers: the simulator does not raise the TX interrupt again (known,
`CLAUDE.md`), so the UART is only refilled on the 1 ms kick. 9 bytes leave per tick, 10 come in, the
512 byte ring fills up, then every tenth frame is dropped. Setting `_U1TXIF` in a 10 kHz interrupt
in the simulator build removes this completely. `scope.c` is not changed for that.

## 3. Slowdown

| Run | cycles/s | slowdown, Stopwatch | slowdown, samples in the file |
|---|---|---|---|
| fast 0 | 2557684 | 12.51 | 12.59 |
| fast 1 | 2137172 | 14.97 | 15.00 |
| fast 2 | 2214634 | 14.45 | 14.51 |
| fast 2, kick | 2258844 | 14.17 | 14.17 |

The slowdown does not grow with the ISR body. The simulator costs about the same per instruction,
and the second timer peripheral costs about 2. The value 25 from `SIMULATOR.md` was not reproduced,
and no run without a stream was made. Machine: the same PC for all runs, no other load controlled.

## 4. Output lag

`s0` is the newest sample in the UART output file just before the write goes in, `s1` the first
sample in the file with the new value. Lag = `s1 - s0`, 1 sample = 1 ms. Write of `probe` with
command `W` through the mailbox, during the stream, 30 s after its start.

| Run | target lag per round, ms | min / median / max | wall |
|---|---|---|---|
| no kick | 58 58 58 58 59 58 59 57 57 59 | 57 / 58 / 59 | 0.8 to 0.9 s |
| kick | 3 3 3 2 3 3 2 3 2 2 | 2 / 3 / 3 | 0.1 s |

The 58 ms are the full TX ring (51 frames) plus what is on the way to the file. 58 ms x 14.5 = 0.84 s
agrees with the wall time, so the file itself adds little. `mdb_serial.py` also spaces mailbox
writes by 1 s wall, which is about 69 ms target time between two commands.

## 5. UxRX_ISR with injected data

`scope.c` got two counters in the scratch copy: `rx_hits` (ISR entries), `rx_bytes` (bytes read).
Each case is a fresh MDB session. `Stim` comes after `Program`.

| Case | rx_hits | rx_bytes | UART output | Meaning |
|---|---|---|---|---|
| `firmware_flag` | 1 | 0 | 0 | firmware sets `_U1RXIF`: vector and counters work |
| `mdb_input_file` | 0 | 0 | 0 | `Set uart1io.input file`, `inputfile`: no effect |
| `scl_packetin_hex` | 0 | 0 | 0 | literal in the call: `E9814-SCL: Parameter is not a variable` |
| `scl_packetin_var` | - | - | 0 | variable with `"P"`: `NumberFormatException`, values must be hex |
| `scl_packetin_value` | 1 | 2 | 9 bytes `SCP1...SC` | `s := "50 50"`: real receive, ping answered |
| `scl_packetin_one` | 0 | 0 | 0 | one byte: `URXBE` = 0, but no interrupt |
| `scl_packetin_stream` | 8 | 16 | 1 byte ACK | configure + run, 17 bytes: run command stays in the FIFO |
| `scl_packetin_stream_pad` | 9 | 18 | 3902 bytes, ACK ACK, frames | with one padding byte: stream runs |
| `scl_accessin` | 0 | 0 | 0 | `accessin` plus flag: no interrupt |
| `scl_regs` | 0 | 0 | 0 | SCL clears `URXBE`, its write of `U1RXIF` has no effect |
| `scl_flag_only` | 0 | 0 | 0 | SCL bit write to `IFS0.U1RXIF`: no effect |
| `scl_word_flag` | 0 | 0 | 0 | SCL word write to `IFS0`: no effect |
| `scl_sync` | 1 | 1 | 7 bytes `SCP1...` | SCL presents the byte, firmware sets the flag, SCL ends it |
| `scl_pin` | 0 | 0 | 0 | UART frame on pin RB6: no effect |
| `mdb_regs` | 1 | 57528 | 0 | MDB `write`: ISR entered, `URXBE` stays 0, ISR never ends |

Result: `packetin(s, U1RXREG, true)` with `s` a `line` variable holding hex values drives the real
receive path into `UxRX_ISR` and on to `scope_rx_byte`. Example in `CASES` of `m0_rx.py`.

Peculiarity: in the simulator the RX interrupt came once per two bytes. One byte alone gives no
interrupt, 2 bytes give 1, 16 give 8, a last odd byte stays in the FIFO with `URXBE` = 0. `scope.c`
leaves `URXISEL` at 0. Whether this is the simulator or also the device is NOT established here. If
the device behaved like this, single byte commands would hang, so M7a has to compare it with the
data sheet. `s` was only tried with values fixed before `Run`; `Stim` during a run was not tried.

## Not tested

- Anything on hardware, including the kick and the real TX interrupt.
- Capture mode with the second timer; a 10 kHz interrupt below mini-scope's priority.
- Slowdown without a stream, or under PC load. The Stopwatch reading every 5 s during the runs
  was not separated out; the agreement with the file slope suggests it costs little.
- The main loop fallback (not needed).
- Configuration `default` (not built, by rule).
